# 网页端实测流程

验证日期：2026-10-12。使用Chrome DevTools MCP，用户自行登录并明确授权真实计次票预约。已完成查询、约号确认、提交、成功页及待出行订单核验；未取消预约或另行支付。
以下可供另一会话直接操作；不保存账号、证件、订单号、URL敏感参数或本次uid。

## 已验证的路径
1. 登录可能落到个人中心，不一定自动返回原计次票入口。
2. 点击“计次•定期票订单”（路径 /otn/view/commutation_order.html），再点击“全部订单”。
3. 从目标产品行核对乘车人、区间、席别、剩余次数和状态，再点该行“立即预约”。
4. 出现乘车人选择弹窗；“去预约”进入查询页，不是最终预约提交。
5. 查询页路径 /otn/view/commutation_queryLeftTickets.html，需由产品行进入，不裸跳以免缺少产品上下文。
6. 修改日期输入框，点击“查询车次”，核对结果标题的实际日期、数量与每班车发到站。
7. 方向切换图标改变发到站，随后点击“查询车次”，核对结果方向。
8. 产品行“预约详情”进入预约记录页；该页URL携带个人和订单参数，只从当前链接打开，不复制完整URL到文档。
9. 详情记录包括日期、方向、车次、席别、席位及状态；“已取消”或历史“出站已检”不能当作本次新预约成功。

## 已观察的易错点
- 默认待支付页为空，不表示没有已购产品。
- 历史产品行有“可预约数：不限次”显示，不能据此将20次产品认定为无限乘坐；结合产品定义及查询页剩余次数确认。
- 本次乘车人弹窗曾显示与订单行不同的示例区间，但进入查询页后显示所选产品区间。允许只读进入查询核对；若查询/确认页仍不一致，禁止提交并重新选择产品。
- 车次列表中二等座和无座各有同名“立即预约”。以车次、席别及余票对应关系定位按钮，而不是使用第一个同名按钮。
- 同产品多个订单时不能仅按“已启用”取第一条；核对真实可用次数及状态，多个实际可用且用户未指定时确认选择。

## 方向图标没有唯一uid时
本次DOM观察到容器 #ticket-station-direction，图标 .icon-qiehuan；运行时先检查它仍唯一且可见。
可对该可见图标调用DOM click，属于页面UI操作，不调用隐藏购票接口：
```js
() => {
  const nodes = document.querySelectorAll('#ticket-station-direction .icon-qiehuan');
  if (nodes.length !== 1 || !nodes[0].getBoundingClientRect().width) {
    return { clicked: false };
  }
  nodes[0].click();
  return { clicked: true };
}
```
随后重新读取出发站和到达站，点击“查询车次”并核对结果。选择器失效时重新观察DOM，不盲目重复。

## 验证边界
已验证：登录恢复、产品定位、进入预约查询、日期查询、往返切换、约号确认、提交、预约成功页、约号订单待出行记录及实际座位。
未验证：取消预约、新产品支付、普通票出票、APP实机。
另一个会话有工具和有效登录可继续上述流程；真实提交需用户提供目标行程并授权。

## 真实提交与成功核验（已实测）
1. 点击车次正确席别的“立即预约”后，出现“约号确认”弹窗，尚未提交。
2. 核对日期、发到站、车次、时间、席别和乘车人；可选座偏好不是保证，未指定偏好时可由系统分配，不必额外追问。
3. 用户已授权该行程后点击“确认约号”，只提交一次。此后可能先显示loading。
4. 等待准确成功文本“预约已成功”，不是“预约成功”；成功页路径 /otn/view/commutation_appointment_successful.html。
5. 等待文本超时先检查当前路径及页面状态，本次文本匹配超时时页面实际已经成功；不能因此重试提交。
6. 成功页读取“订单信息”中的日期、方向、车次、席别和实际席位。
7. 点击“查询订单详情”（快照可能是StaticText，DOM实际为可点击a），进入“约号订单”。
8. 约号订单路径 /otn/view/commutation_ticket_order.html，默认“待出行”；目标记录应显示“已预约”及匹配行程和席位。
9. 已授权行程的记录存在且状态“已预约”才收尾；不点击“取消预约”。若仅成功页出现但记录未加载，先等记录，避免重复提交。
10. 座位可能显示010D或10D，忽略前导零比较同一座位，不把格式差异判断成行程错误。
